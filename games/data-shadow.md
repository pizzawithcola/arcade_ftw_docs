# Data Shadow

主流程第 4 个节点（`type: game`，`game: data_shadow`）。
代码：`arcade_ftw_fe/src/games/dataShadow/`。

**目标设备：iPad 横屏。** 玩家用手指在帖子上**自由拖选**文字。

## 玩法

屏幕上是**一条 LinkedIn 风格的帖子**，作者是某公司的 Head of Customer Experience。
帖子读起来完全正常、积极、专业——但里面泄露了**不该公开的信息**。

1. **点一下子整段**（一段就是一条可举报的内容），整段立刻变成荧光笔高亮。
2. 再点一次同一段就把它**撤出报告**——没有确认弹窗，错误一步的成本是一下点击。
3. 加进报告的段落在正文里保留高亮，并在右侧 **Your report** 面板列出一条（超过三行的部分截断显示）。
4. 面板里可以逐条删除、反复补充。
5. 点 **Submit report** 交卷。

玩家有 **50 秒**判断并提交；提前交卷后会锁定报告，但等到计时结束才统一显示判定。flow 节点为 60 秒，留出 10 秒结果展示。

> 2026-11-01 起从「拖选任意区间」改成「整段点击」：既然粒度是段落，就没有要瞄准的东西，
> 时长也从 80 秒收到 50 秒。

| 结果 | 得分 |
|---|---|
| 抓到文字或图片泄露 | 按严重程度 **+80 或 +120** |
| 误报文字或标记安全图片 | **−80** |
| 漏掉一个泄露 | 0 |

满分 **800**（4 个高价值目标 × 120 + 4 个商业目标 × 80；每次误报 −80）。

### 为什么是「选区旁的气泡」而不是右侧面板的按钮

第一版把 Add 按钮放在右侧面板底部，用户抱怨**注意力不会被吸引**——选完字眼睛还在帖子上，却要去屏幕另一端找按钮。

现在按钮**贴着选区出现**，下一步动作就在视线焦点上。实现细节：

- 用 `rangeForOffsets()` 把字符区间还原成 DOM Range，`range.getBoundingClientRect()` 取包围盒，`position: fixed` 定位在高亮正上方；
- 靠近屏幕顶部（`rect.top < 72`）时**翻到下方**，避免被裁掉；
- 水平位置 clamp 在视口内，避免贴边溢出；
- 按钮 `pointerdown` 时 `preventDefault()`：按下不开始新的扫选，按钮所属的高亮也不会被动到；
- 滚动/缩放也会重算位置。

### 为什么是「整段点击」，而不是拖选

拖选是上一版的做法（自绘荧光笔、`caretRangeFromPoint` 算偏移）。它解决了 iOS 的 copy 面板，
但把游戏变成了瞄准练习：在 iPad 上把选区刚好停在 `35.65%` 上很难，而**评分要求指向具体锚点**。
客户的结论是——判断的粒度本来就该是段落，不是字符。所以：

| 环节 | 做法 |
|---|---|
| 段落 | 每段一个 `<button class="post__para">`，`aria-pressed` 表示是否在报告里；`user-select: none`，浏览器再也拿不到选区 |
| 计分 | 选区就是这一段在 `POST_TEXT` 里的**字符区间**（`blockRange()`），评分逻辑不用改 |
| 计分容错 | `MAX_SELECTION_CHARS` 从 140 提到 **200**（最长一段约 160 字）：一段完整包含锚点即按「指对了」算，两段或整篇仍然不算 |
| 判错 | 点了一段**不含锚点**的内容 → 一次误报（−80），这就是这轮的主要失分方式 |
| 揭示 | 逐段判定：这一段里有漏掉的泄露 → 琥珀色；这一段已加并且抓到了 → 绿色 |
| 图片 | 不受影响，仍是图片右下角的小 ＋ 按钮，和「点开大图」分开 |

### 为什么加入后要在正文里做高亮

只在右侧面板列出来，玩家**看不出自己在全文里的分布**——不知道哪几句已经标过、句子之间有没有重叠。所以加入的文字在正文里保留**荧光笔底色**（`linear-gradient` 画在文字 12%–92% 的高度上，像真的马克笔，而不是整块背景）。

副作用：高亮会把文本节点从 `<mark>` 处切开，所以字符偏移**不能用 `Range.toString()`**（那依赖选区对象的即时状态），改成遍历 `.post__body` 下的所有文本节点累加长度——切分多少次都不影响。同一个累加表反过来用于把字符区间还原成 DOM Range（给气泡定位）。

## 为什么是自由拖选，而不是点预设片段

点预设片段（上一版做法）虽然稳，但用户明确要求**自由选择风险内容**——玩家应该像举报一篇真实帖子那样，用光标/手指圈出那几句话。

代价是**评分必须做区间重叠计算**：选区是字符区间，不是规整的 token。见下。

## 评分：纯度 + 覆盖率

**纯度（purity）** = 选区里落在任何泄露范围内的字符数 / 选区总长度

**覆盖率（coverage）** = 有效选区覆盖某个泄露的比例

规则：

| 条件 | 结果 |
|---|---|
| 选区超过全文 50% | 该条选择无效，记一次误报（−80） |
| 否则，纯度 ≥ **0.30**，或选区不超过 140 字且完整包含一个风险锚点 | 该条选择有效 |
| 有效选区对某泄露覆盖 ≥ **50%** | 该泄露算抓到，按其权重得分（+80 或 +120） |

多条选择覆盖同一个泄露时取**区间并集**，不会重复计分。图片单独标记：抓到风险图片 +120，误报安全图片 −80。

### 阈值 0.30 是量出来的，不是拍的

由于全篇选择会超过 50% 的长度上限，直接全选不会得分；而过短、未完整指向风险短语的选区也会被判为误报。对完整锚点的短拖选设有容错，以适应触屏选字不易精确的情况。

## 当前识别目标

正文有 6 个文字泄露项（其中监管事项有两个可命中的替代锚点），下方有 **1 张风险图片**和 **1 张安全图片**（2026-11-01 从 3 张减到 2 张）：

| 目标 | 权重 | 判定依据 |
|---|---:|---|
| `real customer conversations` | +120 | 涉及真实客户对话及其使用依据 |
| `the regulator verbally approved it` / `formal notice will be announced soon` | +120 | 正式公告前披露监管审批状态 |
| `our internal forecasting` / `2.4 million conversations` | +80 | 暴露内部预测能力或业务规模 |
| `35.65%` | +80 | 暴露内部仪表盘的精确指标 |
| `19 markets` | +80 | 暴露试点的实际覆盖范围 |
| `a top-3 HK retail bank` | +80 | 暴露可识别的客户信息 |
| Sprint Review（仪表盘） | +120 | 图片暴露业务指标 |
| Team Photo | −80（误标时） | 安全照片，不含内部信息 |

> 💡 设计意图：最危险的那条藏在**读起来最像「我们很创新」**的句子里。这就是「data shadow」的含义——泄露往往不像泄露。

## iPad 横屏布局

```text
┌───────────────────────┬──────────────┐
│ Data Shadow · 提示 · 80s              │
├───────────────────────┼──────────────┤
│                       │  YOUR REPORT │
│   LinkedIn 帖子        │  已选文案列表 │
│   （可滚动）            │  （可滚动）    │
│                       │  [Submit]    │
└───────────────────────┴──────────────┘
```

- 两栏 grid：`minmax(0,1fr)` + `clamp(15rem, 27vw, 20rem)`。
- **左右两栏各自滚动**，页面本身不滚（`documentScrolls = false` 已实测）。
- 1024×768（iPad 横屏）实测：帖子 720px、面板 262px，两者同高 659px。
- 窄屏（< 52rem）退化为上下堆叠。

> ⚠️ `.stage` 本身是 `align-items: center` 的 flex。改成 grid 后**必须显式 `align-items: stretch`**，否则右侧面板会被垂直居中、高度缩水（实测 y=203/h=442，正确应为 y=95/h=659）。

> ⚠️ **面板标题必须用两个类**（`.report__head .report__title`）。`.stage h2` 的 `font-size: clamp(1.6rem, 5vw, 3rem)` 与单类 + 元素的 `.report__head h2` **特异性相同**，胜负由样式表顺序决定；实测标题被撑到 **381px 宽、挤在 260px 的头部里**并被裁掉。这和 `.stage` 的 `text-align` 覆盖是同一类坑：**跨文件样式不要依赖导入顺序**。

### 为什么面板要有「Add selected text」按钮

> **已废弃三级**：气泡 → 自绘扫选 → **整段点击**（见上）。保留这段是因为它记录的限制仍然成立——iPad 上不能靠「长按选词自动抓取」接管手势，那会和系统手柄打架。

iPad 上如果用长按选词后自动抓取，会**和系统的选择手柄打架**——用户还没拉完选区就被抓走了。所以触摸端一直保留「必须由用户显式点一下」的一步；现在的区别是这一步变成扫完松手后的气泡按钮，而不是系统选区旁的按钮。

## 只有一个倒计时

顶部 shell 原本还有一个「节点剩余时间」时钟，而游戏自己显示独立的 `80s`——**两个倒计时同屏且数字不同**，玩家会困惑。

现在 shell 的时钟在**自带计时器的游戏屏幕**上隐藏（`ownsTimer()` 判定：hallucination / data_shadow / quiz），屏幕上只留玩家真正在用的那一个。Data Shadow 的 50 秒用于判断；计时结束后显示结果，主流程节点还留有 10 秒供玩家阅读。

## 当前状态与限制

- **内容硬编码在前端**（`content.ts`）：1 条帖子、7 个段落、6 个文字泄露项、2 张图片（1 张风险图、1 张安全图）。
- **原始选择不落库**；结算分数通过 `POST /api/me/score` 按节点幂等上报，并写入 `data_score`。
- 只有一轮，整条帖子**一个总倒计时**（不像 quiz 是每题一个）。
- 玩家选择时长 **50 秒**；flow 节点时长 **60 秒**（另有 10 秒展示判定）。改 `ROUND_SECONDS` 时**必须同步改 `flow.py`**——`test_flow.py::test_data_shadow_gives_the_post_fifty_seconds` 会校验两段时长下限。
- **未在真机 iPad 上验证过**：整段点击由 Playwright 的真实点击验证；真机 Safari 上「点段落」与「滑动查看帖子」是否冲突仍需现场试一次。
