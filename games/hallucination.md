# Hallucination

主流程第 2 个节点（`type: game`，`game: hallucination`）。
代码：`arcade_ftw_fe/src/games/hallucination/`。

## 玩法

一次显示一条 **AI 的回复**，观众用一根**信任刻度条**判断这句可不可信：

```
DOUBT ——————————————— | ——————————————— TRUST
                    中间
```

- 左端 **−200**（确定是编的）→ 中间 **0**（不知道）→ 右端 **+200**（确定是真的），**每格 10 分**，共 41 档。
- 刻度条从中间往你拖的方向生长；**doubt 一侧是黄色、trust 一侧是绿色**，而且**越拖越深**——轻押是浅黄/浅绿，拉到底才是饱和的那支颜色。中间有一道白色刻痕，对着它就是 0 分。
- 题干一行：**CAN YOU TRUST THIS AI RESPONSE, OR SHOULD YOU DOUBT IT?**
- 下方实时显示 **`+140` / if you are correct · −140 if you are wrong**，中间位置显示 `0 / nothing either way`。
- 三档文字 **Doubt / Not sure / Trust** 会亮起当前所在的一侧，颜色跟着同一侧的深浅走。

题目内容是「用户问了什么」＋「AI 答了什么」，玩家只对**回复**做判断。

> **为什么从五个按钮改成刻度条**：五个按钮只能表达五个决定，而且旧阶梯是 `−10 … +20`——两端不对称，导致「判为假」的题最多值 10 分、「判为真」的值 20 分，整轮真实满分只有 40。刻度条让两端都值 200，中间 0 是真正的第三种选择而不是兜底。

> **分数在倒计时结束时才提交**，不是第一次拖动时。玩家在计时结束前可以反复调整，最终按停下的位置计分（`useScoreReport` 保证同题只上报一次）。

## 计分：押对了全额，押错了赔一半

每题有一个**真值**：这句 `trust`（站得住）还是 `doubt`（幻觉）。

```ts
score = 押对 ? +|刻度值| : −(|刻度值| × 0.5)
```

| 情况 | 得分 |
|---|---|
| 句子是真的 + 拉满 Full Trust（+200） | **+200** |
| 句子是幻觉 + 拉满 Full Trust（+200） | **−100** |
| 句子是幻觉 + 拉满 Full Doubt（−200） | **+200** |
| 句子是真的 + 拉满 Full Doubt（−200） | **−100** |
| 句子是幻觉 + 押 140 Doubt | **+140** |
| 句子是幻觉 + 押 140 Trust（押错） | **−70** |
| 任何句子 + 停在 Not Sure（0） | **0** |

整轮上限仍 **600**（3 × 200），下限 **−300**。

**为什么不对称**：

- 这一轮要教的是**敢下判断**。如果输赢对称，最优解永远是「押到 100 就停」——避开风险比看对更划算，那这道题就白问了。
- 赔一半的意思是：押满错一次（−100）刚好等于押满对一半（+100）。**下注永远值得**，只要你有判断。
- `Not Sure` 永远 0：**唯一不会输的选项**，但也永远不赚——它是一张弃权票，不是保本理财。
- 计分集中在 `scoring.ts` 的 `scoreFor()` 与 `LOSS_SHARE` 一个常量。

## 为什么是拖动条而不是五个按钮

五个按钮只能表达五个决定，而且旧阶梯 `−10 … +20` 两端不对称，「判为假」最多值 10 分、「判为真」值 20 分，整轮真实满分只有 40。拖动条把「我有多信」还成一个连续的量：押多重的注由玩家自己决定，两侧各 200，中间 0 是真正的第三种选择而不是兜底。

代价是答案变得更细，所以刻度条必须**一眼就会用**：每格 10、41 档、拖动时下方实时给出 `+140 / −70`，颜色也跟着深浅变化。字幕组不再需要念五个选项，只需要念「往左还是往右」。

## 为什么是「两道幻觉 + 一道站得住」

一个全是陷阱的回合教出来的是「什么都别信」，这本身是另一种失败模式。所以第 2 道（沸水校准温度计）给的是一个**真正正确**的回答——它专门惩罚「看到自信就怀疑」的条件反射。

> ⚠️ 目前是 **2 假 + 1 真**，所以「一路 Full Doubt」稳拿 `+200 −100 +200 = 300/600`（50%），而「一路 Full Trust」只有 `−100 +200 −100 = 0`。赔一半的设计把原来的 33% 抬到 50%，但没有根除偏向——要真正平衡得用 4 道题（每轮多 25 秒），这笔时间账尚未批准。

## 倒计时：跟随引擎的暂停

每道题 **20 秒答题 + 5 秒揭晓 = 25 秒**，三道题共 75 秒；节点给 **78 秒**，末 3 秒是总分页。

**倒计时必须随引擎暂停而冻结。** 曾经用裸 `Date.now()` 实现，结果操作员按了暂停、节点头部时钟停了，但游戏内的倒计时**继续走**，题会在暂停期间被烧掉。这是实测抓到的 bug。

修法不是自己维护第二个时钟，而是**从引擎的状态推导**（`useNodeElapsed`）：

```ts
remainingMs = endsAt !== null ? max(0, endsAt - now) : heldMs
elapsed     = durationMs - remainingMs
```

`endsAt`（playing 时有值）和 `heldMs`（paused 时的冻结值）本来就已经是暂停感知的，所以相减就白拿了「已用时间」，**没有 ref、没有第二个时钟要同步**。playing 时 `now` 增长 → elapsed 增长；paused 时 `heldMs` 恒定 → elapsed 冻结。

实测的完整周期：

| 步骤 | 倒计时 | 结果 |
|---|---|---|
| 暂停中开始 | 20s | — |
| 暂停 +3s | 20s | 冻结 ✓ |
| 恢复 +4s | 27s | 正常走 ✓ |
| 再暂停 +4s | 26s → 26s | 停在 26s ✓ |
| 再恢复 +3s | 24s | **从 26s 续上**，没有跳变 ✓ |

> ⚠️ 一开始我用 `useRef` 累积暂停时长，被 oxlint 的 `react(refs)` 抓出来——渲染期读 ref 在并发渲染下不安全。改成从 store 推导后，两条 lint 都干净了，而且**少了一个需要同步的状态**。

## 当前状态与限制

- **题目硬编码在前端**（`content.ts`），3 道，顺序是**陷阱 → 真正正确的答案 → 陷阱**：
  1. 洗车店 50 英尺该走路还是开车（答案是「开车」，车得在场）——陷阱：流畅但答错了问题；
  2. 用沸水校准温度计（海拔 0 时 100 °C）——**这道是真的**，中间那道必须正确，否则整轮在教「一律怀疑」；
  3. 披萨芝士往下滑（回复里夹了一句「加 1/8 杯无毒胶水」）——陷阱：荒唐指令藏在合理建议后半段。
  题库上线后这里变成测试用的 fixture。
- **纯前端**：答案不落库、不上报，分数只存在于当前页面内存。刷新即清零（靠节点切换重新挂载来重置）。
- **揭晓是每题即时**的。要做成「全场一起揭晓」需要先有答案上报与聚合链路（`scores` 表目前仍是零读写）。
- **超时 = 未作答 = 0 分**，并直接进入揭晓（显示 `Time's up`）。这样一块没人操作的屏幕不会让整场演出停摆。

> ⚠️ **节点时长必须 ≥ 题目总时长**，否则引擎会在玩家答完前切走节点。当前 3 × 25s（20s 抢答 + 5s 判决）= 75s，节点 **78s**，末 3 秒是总分页。改题目数量或 `QUESTION_SECONDS` 时**必须同步改 `flow.py` 的 `duration_sec`**；「节点时长够不够」有测试把关（`tests/test_flow.py::test_question_nodes_outlast_their_questions`），但题数与节点声明仍是两处手写。
